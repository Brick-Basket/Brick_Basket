# Testing

Populated Part 20; extended post-Part-20 stabilization pass (Phase 18); extended again in the BrickBasket final hardening pass (P1 TESTING). Written honestly rather than aspirationally throughout.

## Status: 17 test files — pure math, the REST-client foundation, and adapter workflow coverage; component tests and e2e still don't exist

As of Part 20, this repository had **no test framework configured and no test files at all** (confirmed by direct inspection: no `jest`/`vitest`/`playwright`/`@testing-library/*` dependency, no `*.test.*`/`*.spec.*` file, no config file of any kind), even though `vitest` had already been added as a devDependency in this same stabilization pass's Phase 1/22 dependency cleanup — installed but never wired up. Phase 18 of that pass closed the framework gap and added the first real tests; the BrickBasket final hardening pass then added adapter-level workflow tests. As of this pass, the suite is **17 test files**, in three groups:

**1. Pure math modules (7 files, unchanged since Phase 18).** One `*.test.ts` file colocated next to each pure `*-math.ts` module: `src/components/cost/cost-math.test.ts`, `src/components/dpr/dpr-work-item-math.test.ts`, `src/components/finance/gstr-math.test.ts`, `src/components/finance/tax-record-math.test.ts`, `src/components/payments/payment-math.test.ts`, `src/components/schedule/schedule-progress-math.test.ts`, `src/components/schedule/schedule-monthly-plan-math.test.ts`. Each file covers that module's every exported function: the ordinary case, the documented edge case (divide-by-zero guards, clamping, empty-input aggregates, floating-point tolerance), and — where the module's own doc comment calls one out — the specific behavior that comment promises (e.g. "excludes the DPR currently open," "cumulative not incremental").

**2. The REST-client foundation (1 file, `src/lib/api/http-client.test.ts`, added alongside Phase 21's REST-client scaffold).** Covers `buildQueryString` (empty/omitted-value/serialization/never-emits-the-string-"undefined" cases) and `ApiError` (is a real `Error`, carries `status`/`body`, uses `status: 0` for a request that never reached the server). This file previously existed without being mentioned here at all — a documentation gap fixed in the BrickBasket final hardening pass (P2 documentation cleanup); it is **not** one of the seven pure-math files above, which is why earlier phases' "seven test files" framing undercounted the real total (eight, at that point).

**3. Adapter workflow tests (9 files, new in the BrickBasket final hardening pass).** Colocated next to their adapters in `src/lib/api/adapters/`, covering the 11 workflows named in this pass's directive:

| Test file | Workflow(s) covered |
|---|---|
| `contracts-adapter.test.ts` | Contract: send → accept/decline |
| `requisitions-adapter.test.ts` | Purchase Requisition: submit → approve/reject |
| `rfq-adapter.test.ts` | RFQ: quote → comparison → finalize |
| `purchase-orders-adapter.test.ts` | PO: L1 → L2 → release/issue |
| `store-requisitions-adapter.test.ts` | Store MR: draft → submit → approve/reject → issue |
| `dpr-adapter.test.ts` | DPR: create → schedule contribution; edit → contribution corrected; remove/relink schedule line → old contribution reconciled (all three DPR/Schedule workflows in one file, since they share the same fixture activity and build on each other) |
| `grn-adapter.test.ts` | GRN: receipt constraints (issued-PO-only, non-empty lines, line must belong to the given PO) |
| `mrc-adapter.test.ts` | MRC: issue/customer response, plus the `source: "grn"` received-quantity cap |
| `cost-to-complete-adapter.test.ts` | Cost-to-complete: core derivation (ACE/RFQ/PO category tracing, `unallocatedOrderedTotal`, the empty-report case) |

These build fresh entities through each adapter's own real `create`/`submit`/`decide`/`finalize`/etc. methods (never a mock array directly) via a small shared, non-test fixture helper, `src/lib/api/adapters/test-fixtures.ts` — deliberately named so it does **not** match this repo's `include: ["src/**/*.{test,spec}.{ts,tsx}"]` Vitest pattern and isn't picked up as a suite of its own. This mirrors the adapters' own cross-adapter composition discipline (`RFQAdapter.create` calling `requisitionsAdapter`, e.g.), so a test walking "an issued Purchase Order" exercises the same guardrails (approved-only, finalized-only, issued-only, ...) a real user would hit. Per this pass's explicit instruction, this is deliberately **not** 100% coverage — it targets the 11 named workflows' happy paths and their most important guard-rail rejections, not every branch of every adapter method.

`npm test` (`vitest run`) is a real, runnable command.

**Verification note, updated now that this suite has actually been run.** Every earlier claim in this file said, correctly at the time, that none of these 17 test files had ever been executed — this sandbox still has no npm registry access, so that remains true *here*. But the project owner ran `npm install && npm test` in their own environment (with real npm access) and reported the real results back, and this pass (the "Real build/test verification pass," see `docs/CHANGELOG.md`) fixed what that run actually found: **100 of 112 tests passed on the first real run** — every pure-math and REST-client assertion was correct as hand-traced. Two real, narrow issues surfaced and were fixed:
1. One test in `dpr-work-item-math.test.ts` ("excludes lines for a different work item entirely") asserted against the wrong work-item id — it queried for the *history's own* "different" item (`electrical_1`) instead of an item with no entries at all, so it was asserting the wrong thing, not catching a bug. The underlying `getPreviousQty` function was already correct (its sibling test already covered exclusion). Fixed by querying a genuinely absent id.
2. 11 adapter-workflow tests (`grn-adapter`, `mrc-adapter`, `purchase-orders-adapter`, `cost-to-complete-adapter`) failed with `Test timed out in 5000ms` — not an assertion failure. `test-fixtures.ts` composes several real adapter calls end-to-end (Requisition → RFQ → PO, sometimes → GRN/MRC/Cost-to-Complete too), each with its own simulated network `delay()`; the longest chains (e.g. `createIssuedPurchaseOrder`) add up to ~6-7 seconds, over Vitest's 5000ms per-test default. Fixed by raising `testTimeout` in `vitest.config.ts` to 20000ms — no adapter logic changed, since none of the underlying business rules were wrong.

`tsc --noEmit` also surfaced 38 real `noUncheckedIndexedAccess` errors across 8 files (array/object destructuring and indexing this project's `strict`/`noUncheckedIndexedAccess: true` config correctly flags as possibly-`undefined` at the type level, even where a runtime invariant guarantees otherwise) and `npm run lint` failed outright because ESLint 9 no longer reads the legacy `.eslintrc.json` at all and no `eslint.config.*` existed yet. Both are fixed in the same pass — see `docs/CHANGELOG.md`'s "Real build/test verification pass" entry for the full file list. Whoever next changes one of these adapters or test files should still run `npm test`/`npm run typecheck`/`npm run lint` before trusting a change — this was the first real run, not a guarantee against the next one finding something new.

What existed before Phase 18 and still applies for code outside these 17 files: `npm run lint` (ESLint, `eslint-config-next`, now via flat config — `eslint.config.mjs`) and `npm run typecheck` (`tsc --noEmit`, `strict: true` + `noUncheckedIndexedAccess: true`) remain real but different classes of bugs than a behavioral test catches, and every verification claim in this app's docs for code outside the 17 test files above still means "read carefully and reasoned about manually," not "covered by a test" — this pass fixed what one real run found, it didn't add new tests.

## What a real implementation should add next

In priority order, continuing from where this pass stopped:

1. ~~**Unit tests for the pure `*-math.ts` modules.**~~ **Done** (Phase 18) — all seven, listed above.
2. ~~**Adapter tests for the highest-value workflows.**~~ **Done** (BrickBasket final hardening pass) — the 11 workflows listed above, across 9 files. Not exhaustive: every other adapter method not explicitly named above (there are 25+ adapter files in total) still has no test, and even the 9 covered adapters aren't tested to 100% branch coverage, by explicit instruction. The next-highest-value adapter-level gap, if this is picked up again, is probably the Store — GRN "split deliveries across multiple GRNs against one PO" case (`docs/OPEN_QUESTIONS.md` #32b) and the Notifications/OpsMetrics pure-aggregate adapters (Part 19), neither of which this pass's 11 named workflows covered.
3. **Component tests** for the form layer — asserting that each `docs/VALIDATION_RULES.md` rule actually blocks submission and surfaces the right message, and that `GRNCreateForm`'s hand-written validation (the one form with no zod schema at all) behaves the same way its sibling forms do despite the different mechanism. `@testing-library/react` is the natural fit given `react-hook-form` is already the form layer everywhere. Still not started.
4. **End-to-end tests** for the handful of genuinely cross-page workflows documented in `docs/WORKFLOWS.md` — a Requisition → RFQ → PO → GRN chain, a Contract → customer-portal accept/decline round trip, a DPR line pushing a new `ScheduleProgressEntry` (Part 14's cross-module side effect, `docs/OPEN_QUESTIONS.md` #35d — now largely exercised at the adapter level by `dpr-adapter.test.ts`, but never through actual rendered pages/routes). Lowest priority of the four because it's the most expensive to write and maintain, and the mock-adapter architecture (see `docs/ARCHITECTURE.md` section G) means most of what an e2e test would catch, an adapter test already catches more cheaply.

Whoever picks this up should also decide, before writing more adapter tests, whether the eventual real backend replaces the mock adapters in the same repository (in which case adapter tests get rewritten against the real implementation rather than kept as permanent mock-only coverage) or whether the mock adapters stay as a fixture/demo mode indefinitely (in which case adapter tests are worth keeping long-term) — see `docs/API_INTEGRATION_GUIDE.md` for the cutover plan either way.
