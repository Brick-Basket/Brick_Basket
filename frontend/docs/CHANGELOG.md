## Added an "Overall Progress" readout to the Project Schedule page

Owner asked, after walking through `/admin/project-management/schedule`: the page shows per-activity progress (table + Gantt bar fill) but where does the *whole project's* overall percentage show up?

It already existed — just one screen away. `computeScheduleBasedProgress` (`src/lib/utils/project-progress.ts`, from the earlier "robust progress mapping" pass) already reduces a project's Schedule activities into a single duration-weighted completion figure, and that number already powers two places: the Customer Detail screen's `CustomerProjectProgress` editor (where staff accept or manually override it as `Project.progressPercentage`, with an audit trail) and the customer portal's own read-only `ProjectProgressSummary`. Nothing on the Schedule page itself ever showed it, though — someone looking at the Gantt/table had to navigate to that project's Customer record just to see what their own entries added up to.

Added `ScheduleOverallProgress` (`src/components/schedule/schedule-overall-progress.tsx`), a small read-only card rendered above the Gantt chart on `/admin/project-management/schedule`, for whichever project is currently selected. **Deliberately not a second, competing progress figure** — it calls the exact same `useScheduleBasedProgress` hook and shows the exact same duration-weighted number the Customer Detail screen and customer portal already display, just surfaced one level earlier, right next to the per-activity data it's computed from. No new formula, no new state, no write path: it's a readout only, with no edit control — `Project.progressPercentage` (the figure actually shown to the customer) still only changes from `CustomerProjectProgress` (`customers:write`), untouched by this addition. Renders nothing when a project has no Schedule activities at all (the page's existing "No activities yet" empty state already covers that case) or while loading, and gracefully shows "0%" with no "as of" line for a project whose activities exist but have no progress entries logged yet.

Re-verified live: selected Luxury Villa (5 activities, 2 completed, 1 overdue at 50%, 2 not yet started) and confirmed the card reads "Overall Progress — 43% — Site data as of 05 Sept 2026, 05:30 am — Duration-weighted across every activity below," matching the same duration-weighted math already in use elsewhere, with zero console errors.

## Fixed "New MRC" (and the edit view of any draft/declined MRC) crashing the whole admin section with "This section couldn't be loaded"

Owner reported, screenshot of `/admin/stores/mrc/new`: clicking "New MRC" from the Material Receipt Certificates list immediately replaced the page with the admin app's generic error boundary ("This section couldn't be loaded... Try again, or use the sidebar to go somewhere else").

Root cause, in `src/components/mrc/mrc-line-items-editor.tsx`: its import line pulled `useEffect` from `"react-hook-form"` —

```ts
import { useEffect, useFieldArray, useWatch, ... } from "react-hook-form";
```

— but `react-hook-form` has no export named `useEffect` (it only exports its own hooks; React's own primitives come from `"react"`). The import silently resolved to `undefined` rather than failing at build time, so the component's own `useEffect(...)` call (the one that clears an out-of-scope GRN-sourced line when the selected project changes) threw `TypeError: ... useEffect is not a function` the instant `MRCLineItemsEditor` rendered — confirmed via the browser console: `TypeError: (0 , react_hook_form__WEBPACK_IMPORTED_MODULE_7__.useEffect) is not a function`, caught by `(internal)/admin/error.tsx`'s segment-level error boundary. Since `MRCLineItemsEditor` is an unconditional part of `MRCForm`, this broke **every** path into that form — not just `/admin/stores/mrc/new`, but also editing any `draft`/`declined` MRC via `/admin/stores/mrc/[id]/edit`.

Fixed by importing `useEffect` from `"react"` instead, where it actually lives, same as every other component in this codebase. Re-verified live: clicking "New MRC" now renders the full create form (Customer/Project selects, the Material Lines editor, Notes, Cancel/Create Draft MRC) with zero console errors, where it previously crashed before any of that rendered.

**Note on diagnosis** — this session's local staging copy of the frontend (`/mnt/user-data/uploads/frontend`) turned out to be missing several files that do exist on the actual device (notably all three MRC route files: `mrc/new/page.tsx`, `mrc/[id]/page.tsx`, `mrc/[id]/edit/page.tsx`), which briefly looked like a much bigger "routes were never built" bug before re-staging the real files from the device showed they were present and fine — the local copy is a partial mirror assembled from whatever's been staged over the course of this session, not a full checkout, and shouldn't be treated as authoritative for "does this file exist" questions going forward; `device_list_dir`/`device_stage_files` against the actual device is the source of truth.

## Added a live warning when a Stock Statement entry's Closing Stock would go negative

Owner noticed, following up on the Stock Statement/"Use these values" screenshots above: clicking "Use these values" against Luxury Villa/Cement (no prior Opening Stock recorded for that project — a seed-data gap, not a bug) filled Consumed Today with 60 (traced from that project's approved 60-bag Material Requisition) while Opening Stock and Received Today both stayed 0, producing a Closing Stock of **-60** — already visible in the table in the existing `text-warning` amber styling, but with nothing anywhere explaining *why* a negative number was being shown, or that the form itself hadn't actually checked it.

`StockEntry.closingStock` is always computed as `openingStock + receivedToday - consumedToday` (see `src/types/domain/stock-entry.ts`'s own header comment) and the create/edit form never validated that the result makes physical sense — the three inputs just feed the arithmetic, however implausible. Added a live warning box to `StockForm` (`src/components/stock/stock-form.tsx`) that mirrors this same computation as the user types and shows an amber alert the moment the resulting Closing Stock would be negative, naming the exact figure and prompting a check of Opening Stock before saving.

**Deliberately a warning, not a hard block** — unlike GRN's `assertWithinOrdered`, which does reject an over-receipt outright, Stock Statement is explicitly documented as a manually entered reconciliation ledger (see the form's own "Traced from other Store Management records... nothing here is written in automatically" note), and Stores staff may legitimately need to save an observed shortfall for investigation — e.g. precisely this case, where an earlier day's Opening Stock was simply never logged in this demo's seed data for Luxury Villa. The "Add Entry"/"Save Changes" button stays enabled; this only adds visibility, not a new restriction. Re-verified live: filling Consumed Today with 60 against Opening Stock 0 and Received Today 0 correctly surfaced "This would make Closing Stock -60 — more was consumed than was ever received or carried over as opening stock..." immediately, with submission still permitted.

## Fixed the shared `Dialog` component clipping tall content, making long forms (e.g. "Add Stock Entry" after "Use these values") unreachable past the viewport edge

Owner reported, two screenshots of `/admin/stores/stock`'s "Add Stock Entry" dialog: after filling in Project/Material/Unit/Date and clicking "Use these values" on the GRN/MR/Wastage reconciliation aid (which adds a sizeable info box to the form), the dialog grew taller than the browser window — the "Supplier," "Remarks," and Cancel/Add Entry controls below the aid box were all unreachable, with no scrollbar anywhere to get to them. The empty-form state (no reconciliation box) fit fine and wasn't affected.

Root cause, in the shared base primitive `Dialog` (`src/components/ui/dialog.tsx`, not anything specific to Stock Statement's form): the modal panel `<div>` had no height cap and no `overflow` of its own — just `p-6` padding around whatever `children`/`footer` it was given. The overlay centers it with `items-center` inside a `fixed inset-0` container, so once content got taller than the viewport, the panel simply overflowed equally above *and* below the screen (visible in the owner's first screenshot: the dialog's own title "Add Stock Entry" was already clipped off above frame). `Dialog` also locks `document.body`'s scroll while open, so there was no way to reach the clipped portion by scrolling the page either — the content was just gone until the dialog was made shorter or the browser window taller.

This isn't a Stock-Statement-specific bug — `Dialog` is the shared primitive behind 19 call sites across the app (Wastage, Material Requisitions, Schedule, every Finance module, Leads, PO detail, RFQ detail, the generic confirmation dialog, etc.), so any of them could hit the same wall with a long enough form, a wide validation-error list, or just a smaller/shorter browser window. Fixed at the primitive level: the panel now has `max-h-[85vh] overflow-y-auto` (plus `flex flex-col` to keep it well-behaved), so it always stays fully on-screen and scrolls internally instead of spilling past the viewport — title, body, and footer scroll together. Re-verified live: with the dialog open and the browser window resized down to force overflow (content height 722px vs. a 425px-capped panel in a 500px-tall window), the panel's own `overflow-y: auto`/`max-height: 425px` were confirmed applied, and scrolling the panel to its end brought the "Add Entry" button fully inside the viewport (previously impossible, since the whole panel — not just its content — had no height limit at all).

## Fixed the generic "Record GRN" entry point landing on a stale, previously-visited Purchase Order instead of an empty picker

Owner reported, two screenshots: a GRN (`BB-GRN-2026-007`) correctly recorded against a Luxury Villa PO, then clicking the plain "Record GRN" button on `/admin/stores/grn` (no PO pre-selected via the link, unlike the PO detail page's own "Record GRN" button which passes `?poId=...`) landed on the form with "BB-PO-2026-001 — Manek Tiles & Sanitaryware" already showing in the Purchase Order field — a PO whose lines are both already fully received, not a useful or expected default.

Root cause, in `GRNCreateForm` (`src/components/grn/grn-create-form.tsx`): `const [selectedPoId, setSelectedPoId] = useState(poIdParam ?? "")` only reads the `?poId=` query param on this component's *first* mount — a React `useState` initializer never re-runs on its own. Next.js's App Router does not remount a page component on a search-params-only navigation within the same route, so going from `/admin/stores/grn/new?poId=po_1` (reached earlier from that PO's own detail page) to `/admin/stores/grn/new` (the generic button, no query string) reuses the same mounted `GRNCreateForm` instance. `poIdParam` itself updates to `null` correctly — which is why the field stopped being disabled — but the stale `selectedPoId` from the earlier visit was never cleared, so the dropdown kept showing whatever PO had last been opened via a pre-filled link, however unrelated or already fully received.

Fixed by adding a `useEffect(() => setSelectedPoId(poIdParam ?? ""), [poIdParam])` to keep `selectedPoId` in sync with the URL on every navigation into this page, not just the first. Re-verified live against the running app by reproducing the exact navigation path (PO detail page's pre-filled "Record GRN" link → breadcrumb back to the GRN list → the list's own generic "Record GRN" button, all client-side, no full reload): the Purchase Order field now correctly resets to the empty "Select an issued Purchase Order…" placeholder and the Record GRN button is disabled until a PO is actually chosen.

## Fixed GRN creation defaulting every line to the full ordered quantity even when it was already (partially or fully) received, plus a related ghost-record bug

Owner reported, screenshot of `/admin/stores/grn/new?poId=...`: clicking "Record GRN" against an issued PO failed with `"Scaffolding coupler clamps": receiving 150 would bring the total received to 300, more than the 150 ordered (150 already received across other GRNs)` — and was confused, since the PO's own detail page had just shown "No goods have been received against this PO yet" moments before.

The over-receipt guard itself (`GRNAdapter.create`'s `assertWithinOrdered`, added in an earlier pass — `docs/OPEN_QUESTIONS.md` #32b) was never wrong: it only throws when the sum of received quantities across every GRN on that PO line would genuinely exceed what was ordered, and this build does allow more than one GRN per PO (split deliveries). The real gap was upstream of it: `GRNCreateForm` (`src/components/grn/grn-create-form.tsx`) had no idea how much of a PO line had already been received across earlier GRNs — it always defaulted every line's "Received Quantity" to the full *originally ordered* amount, every time the form loaded for that PO, including a second visit after an earlier GRN had already been recorded (e.g. navigating back after a successful submit, or reopening "Record GRN" from the PO detail page). Resubmitting that stale, always-full default silently overshot what was actually still outstanding — the guard was catching a real over-receipt, but from the form alone it read as a miscount, especially right after seeing "no goods received yet" on the PO itself (which reflects whether a GRN *exists*, not whether this specific attempt's proposed quantity makes sense against what's already recorded).

Fixed by making the form received-quantity-aware: a new `useAllGRNLineItems` hook (`src/hooks/use-grn.ts`) exposes every GRN line item across every GRN (reusing `GRNAdapter.listAllLineItems`, the same method the MRC picker already relies on for a different purpose), and `GRNCreateForm` now sums each PO line's already-received total from it, defaults "Received Quantity" to the **remaining** outstanding amount (ordered minus already received, never below zero) instead of the full ordered amount, and shows that context inline — "X of Y already received across earlier GRNs on this PO — Z remaining," or "Already fully received" when there's nothing left to receive. Re-verified live: `po_1`'s Interior Emulsion Paint line (180 litre ordered, already fully received across its two existing GRNs) now correctly shows "Already fully received" and defaults its Received Quantity input to 0, instead of silently proposing 180 again.

**Found and fixed a second, related bug while investigating.** `GRNAdapter.create` committed the new GRN header to `this.grns` *before* validating its lines — so a thrown over-receipt error (exactly what the owner hit) still left a real, line-item-less "ghost" GRN behind: a consumed `grnNumber`, and a misleading entry in the PO detail page's "Goods Receipt Notes" list (which lists purely off `GRNsAdapter.list({ purchaseOrderId })`, with no check that a GRN actually has any lines) claiming something had been received when nothing had. `create()` is now properly all-or-nothing — the GRN header is only committed alongside its line items, once every line has passed validation, so a failed attempt leaves no trace at all. (If the owner's own browser session has a leftover empty GRN entry from the earlier failed attempt, a full page reload clears it — nothing in this mock build persists past a reload.)

Also fixed a stale doc comment found in the same area: `src/types/domain/grn.ts`'s header comment on `GRN` still said the over-receipt limit "is not enforced... left to the backend" — directly contradicting the guard that's actually been shipped and enforced since the earlier #32b pass. Corrected to describe what's actually implemented.

## Fixed Accepted Cost Estimate's Sr. No. column showing out of order when grouped by category (e.g. 3, 4, 1, 2, 5)

Owner reported (screenshot, `/admin/supply-chain/ace`, Luxury Villa): the Sr. No. column read 3, 4, 1, 2, 5 top to bottom instead of 1 through 5 in order.

This is exactly the scenario `docs/MANUAL_QA_CHECKLIST.md` 1.5 already called out to check for ("the numbers don't update correctly when the list is filtered/grouped... numbering should still run in order within what's visible") — a real, confirmed bug, not a demo quirk. Root cause, in `GroupedACETable` (`src/components/ace/ace-table.tsx`): the Sr. No. shown for each row was computed from that item's position in the incoming `items` prop — which arrives sorted alphabetically by item description — but rows are never actually rendered in that order on this page. They're bucketed into `groups` by category first (Civil, Electrical, Plumbing & Sanitary, etc., in `CONTRACT_CATEGORY_ORDER`), so a row's Sr. No. reflected its alphabetical rank rather than its position in the category-grouped list it actually appears in. For Luxury Villa's 5 items, alphabetical order is Copper Wiring Cable (1st), CPVC Pipe (2nd), OPC Cement (3rd), TMT Steel (4th), Vitrified Tiles (5th) — but category-grouped display order puts the two Civil items (OPC, TMT) first, so they showed "3" and "4" at the top of the list, with Electrical's Copper Wiring showing "1" further down, and so on — exactly the 3, 4, 1, 2, 5 reported.

Fixed by building the Sr. No. lookup from `groups`' own flattened, already-category-ordered sequence instead of the raw `items` prop, so numbering always counts 1, 2, 3... in the exact order rows render on screen, regardless of category. The flat/ungrouped table view (`groupByCategory={false}`, not used on `/admin/supply-chain/ace` today but kept as an option on `ACETable`) was already correct and untouched — its rows render in the same order `items` arrives in, so its Sr. No. always matched. Re-verified live against the running app: Luxury Villa's grouped list now reads 1, 2, 3, 4, 5 in order; Commercial Complex's 4-item grouped list (Civil ×2, Electrical, Mechanical) also confirmed correct.

## Fixed the topbar Project Selector dropdown running off the screen with no way to scroll to the rest of the list

Owner reported, from the running app (screenshot, Stock Statement page): opening the topbar's Project dropdown and moving the cursor down didn't scroll the list — the projects below where the cursor stopped just weren't reachable.

Root cause: `src/components/shell/project-selector.tsx`'s popover `<ul>` had `overflow-hidden` and no height cap at all. With only 3-4 projects this never mattered — the list was always shorter than the screen. Now that there are 6 (Commercial Complex, Luxury Villa, Modern Residence, Riverside Apartments, Heritage Resort, and the newly-added Gorakhpur Business Park), the list runs past the bottom of the viewport; `overflow-hidden` clips whatever doesn't fit instead of scrolling it, and there was nothing to make the page itself scroll either, since the popover is positioned off the trigger button, not the page. The lowest project(s) were simply unreachable by mouse or by scrolling.

Fixed by capping the list at `max-h-80` and switching to `overflow-y-auto` (plus `overflow-x-hidden`, to keep the rounded corners clipping the hover background the same way `overflow-hidden` used to) — the list now scrolls internally once it's taller than that, instead of silently cutting off. No change to the keyboard-navigation behavior (Arrow keys/Home/End already worked and still do; this only affects mouse/scroll-wheel use of the open list).

**Follow-up — the owner reported "same issue" with two more screenshots after the fix above, which turned out to be a second, related bug.** `AppShell` (`src/components/shell/app-shell.tsx`) has no sticky/fixed header — the whole page (sidebar, topbar, this dropdown riding along with its trigger) is one ordinary scrolling document. The list's own internal scroll range is short (6 projects barely taller than `max-h-80`), so a mouse-wheel scroll would absorb that short range almost immediately and then *chain* to the page itself, scrolling the entire app (visible in the owner's second screenshot: a gap opens above the sidebar logo and the topbar drops down) — which read as "the projects above aren't moving," since the list's own scroll had already maxed out and the page moving underneath it doesn't look like the list scrolling. Added `overscroll-contain` to the list, which stops a scroll gesture from chaining past the list's own top/bottom edge — scrolling this dropdown no longer drags the rest of the page with it.

**Second follow-up — the owner reported "I can't reach above [the] selected one," with a screenshot showing the list's scroll stuck just below a selected project.** This was a third, genuinely different bug, not another symptom of the two fixed above: `ProjectSelector`'s "focus the selected option when the list opens" effect was keyed on `[open, projects, selected]`, so it refires — and refocuses the already-focused selected option — on *any* render where `projects` or `selected` get a new reference, not only when the list actually opens. The deeper cause was in `ProjectProvider` (`src/components/providers/project-provider.tsx`): its context value was a fresh `{ projects, selected, setSelectedId }` object literal on every render, so every re-render of the provider (for any reason) handed every consumer, including this dropdown, a "changed" context value even when nothing in it had actually changed — which re-ran the focus effect, and refocusing an element the browser already considers focused still re-triggers its default scroll-into-view, snapping the list back toward the selected row. Net effect: any manual scroll upward kept getting silently undone a moment later. Fixed both layers: `ProjectProvider`'s context value is now `useMemo`'d so it only changes when `projects`/`selected`/`setSelectedId` genuinely do, and `ProjectSelector`'s focus effect now has a ref guard so it only actually calls `.focus()` once per "open" session, never again until the list is closed and reopened.

**Third follow-up — the owner reported "same issue" again with another screenshot, identical scroll position (Luxury Villa cut off at top, Modern Residence first fully visible).** The previous fix stopped the *repeated* re-snapping, but didn't address the real cause the owner's screenshots were actually showing: even a single, correctly-guarded `.focus()` call on the selected option (Modern Residence, 3rd of 6 projects) makes the browser apply its own default scroll-into-view the moment that option isn't already fully visible — which on a list this short, it usually isn't right at `scrollTop: 0`. So the very *first* open was already scrolling the first project(s) out of view, before the owner had touched a scroll wheel at all; it wasn't actually "stuck," there was just never a moment where the top of the list was shown. Fixed by decoupling "move keyboard focus to the selected option on open" (still wanted, for Arrow-key navigation to start in the right place) from "let the browser scroll to make that focus visible": the on-open focus call now passes `{ preventScroll: true }`, and the list's `scrollTop` is explicitly reset to `0` right after — so opening the dropdown always starts showing the first project, with the selected one simply marked (checked, highlighted red) wherever it falls in the list, never auto-scrolled past. Keyboard Arrow-key navigation is unaffected — it still scrolls normally to follow focus, since only this one initial call needed `preventScroll`.

**Fourth follow-up — the owner reported "same issue" a fifth time, with a screenshot that looked unchanged from before.** Four verified, individually-reasonable fixes producing an apparently identical result was the signal that every fix so far had been treating the wrong problem. This time, rather than reasoning from another screenshot, the dropdown was opened directly against the owner's own running app (`localhost:3000`, signed in as Admin) and its on-screen position was measured programmatically (`getBoundingClientRect`, `window.scrollY`) instead of guessed at. That measurement showed `window.scrollY` at `0` and the list's own `scrollTop` at `0` the entire time — **the page was never scrolling, and nothing was being clipped.** All three previous "scrolling" fixes (max-height/overflow-y-auto, overscroll-contain, preventScroll + scrollTop reset) were correct in themselves but were never the actual bug.

The real defect was positioning, present since before any of this thread started: `src/components/shell/project-selector.tsx`'s popover `<ul>` was `absolute` with no `top-*` class. With `top` left at its default (`auto`), the browser falls back to computing the element's position from where it would have landed in normal document flow — and because the popover's parent (`containerRef`) is a `flex items-center` row, that fallback *vertically centers* a tall absolutely-positioned box around the row's center line instead of placing it below the row. Measured live: with the list at its capped ~320px height, its top edge sat at **-124px relative to the viewport** — almost entirely above the visible window — on the very first open, every single time, regardless of scroll position or which project was selected. That's exactly what every screenshot across all five reports showed: the first project(s) always missing from view, looking unreachable no matter how the list was scrolled, because the top of the list was never on-screen to begin with.

Fixed with one additional class: `top-full`, which pins the popover to the bottom edge of its (short, button-height) container instead of relying on the broken auto-position fallback; the existing `mt-2` now does what it always looked like it should — add a small, intentional gap below the trigger. Re-verified live after the fix, in the owner's own running app: the list's top edge now lands at `58px` (trigger bottom + the 8px gap), all six projects render fully on-screen with no scrolling required, and reopening with Modern Residence selected (the exact scenario from the second/third/fourth reports) shows the complete list with nothing cut off. The three earlier CSS changes (`max-h-80`/`overflow-y-auto` for when the project list eventually outgrows 320px, `overflow-x-hidden`, `overscroll-contain`) and the context memoization are unrelated bugs that were real and worth fixing, but none of them were the cause of what the owner was actually seeing — this one is.

## Fixed a real cross-project data bug in Material Receipt Certificates (MRC), explained the GRN/MRC confusion, and added a third mock project (Gorakhpur Business Park)

Owner reported, from the running app (4 screenshots): a GRN recorded against one project showed "No GRNs match these filters" when the Commercial Complex project was selected, and a Material Receipt Certificate (`BB-MRC-2026-005`, for customer Rohan Verma / project "Commercial Complex") showed a line reading "Interior Emulsion Paint" paired with "Certificate CERA-WC-2026-014" — a certificate number that, in this app's own seed data, belongs to a different material (a Sanitaryware WC Set) entirely. Asked to find what's missing, fix it, and explain where a "material order receipt" is shown in the app.

**(1) Where GRN and MRC are actually shown — this was the root of the confusion.** There are two separate "receipt" documents in BrickBasket, easy to conflate:
- **GRN (Goods Received Note)** — Stores → Goods Received Notes. Recorded by Store Staff the moment materials physically arrive against an issued Purchase Order. This is the internal receiving record.
- **MRC (Material Receipt Certificate)** — Stores → Material Receipt Certificates (and the customer's own `/dashboard/mrc`). A customer-facing certificate that selects a customer, a project, and a set of materials to certify — either typed in by hand, or picked `"From Received Goods (GRN)"` to certify a line that was already received. It's a downstream, customer-acceptance document, not the receiving record itself.

**(2) The GRN list showing empty under "Commercial Complex" is correct, expected behavior, not a bug.** The GRN(s) the owner recorded were against Luxury Villa (vendor Vaidya Electricals, PO `po_kmjbxw74`) — switching the Global Project Selector to "All projects" correctly showed them, and switching to "Commercial Complex" correctly showed nothing, because that GRN simply isn't for that project. The Global Project Selector audited and fixed earlier this session is working as intended here.

**(3) Found and fixed a real bug: the MRC form's GRN-line picker let a line from one project get certified on an MRC for a completely different project, with no warning — and a related stale-field bug produced exactly the mismatched certificate the owner saw.** Two separate issues in the MRC create/edit form (`src/components/mrc/mrc-line-items-editor.tsx`, `src/hooks/use-mrc.ts`):
  - `useGRNLinesForPicker` (backing the "From Received Goods (GRN)" dropdown) fetched *every* GRN line in the entire system, regardless of which project the MRC itself was for. Combined with `MRC.customerId`/`MRC.projectId` being intentionally decoupled (see `src/types/domain/mrc.ts`'s header comment, mirroring Contract — still an open, owner-unconfirmed design decision, docs/OPEN_QUESTIONS.md #6/#33), nothing stopped a line received against Project A from being certified on an MRC for Project B/Customer X. Fixed: the hook now takes an optional `projectId` and the picker only lists GRN lines from that project (via `GRNAdapter.list`'s existing `projectId` filter); `MRCForm` now watches its own `projectId` field and passes it through. Leaving "No project yet" selected still shows every line, same as before. If the project is changed *after* a line was already picked from what's now an out-of-scope project, that row is automatically cleared rather than silently submitting a stale cross-project reference.
  - Separately, in `MRCLineItemsEditor`'s `handleGrnLineChange`: switching the "Received Line" dropdown always correctly reset the description/UOM/make/quantity fields to match the newly-picked line — but the Warranty Terms field was only ever *set* when the new line had its own certificate number, never *cleared* when it didn't. This sandbox has no npm registry access, so this exact class of bug — a React Server Components serialization violation, only caught at real build/runtime, not by static review or a bracket-balance check — was invisible here until the owner's own `npm run dev` surfaced it.

- **Root cause**: `src/components/marketing/services-grid.tsx` was converted to `"use client"` in the Hindi pass (for `useLanguage()`) but kept accepting `services: PublicService[]` as a prop. `PublicService.icon` is a `LucideIcon` component reference (a function/forwardRef object, not plain data), and both callers — `(public)/page.tsx` and `(public)/services/page.tsx` — are Server Components, so `<ServicesGrid services={CONFIRMED_SERVICES} />` had to serialize that icon reference across the Server→Client boundary, which Next.js rejects at runtime. This is a general rule, not specific to this component: a Client Component may safely *import* data (including icon components) from a shared module — that's plain client-side bundling — but a Server Component parent may only pass **plain, serializable** values (strings, numbers, booleans, plain objects/arrays of those) as props into a Client Component.
- **Fix**: `ServicesGrid` now imports `CONFIRMED_SERVICES` directly from `src/lib/content/public-site.ts` itself and takes no props at all — the same already-working pattern `WhyUsSection`/`HowItWorksSection`/`ComparisonSection` use for their own local data. The now-obsolete `services={CONFIRMED_SERVICES}` prop (and, on the Home page, the now-unused `CONFIRMED_SERVICES` import) was removed from both call sites.
- **Verified not to recur elsewhere**: `PortfolioGrid`'s `projects` prop (`CONFIRMED_PROJECTS`) was checked and is safe as-is — `PublicProject` (`title`/`location`/`category`/`image`) is plain string data with no icon or function field, so passing it as a prop across the Server→Client boundary is fine. Every other section component added or converted to `"use client"` in the Hindi pass (`WhyUsSection`, `HowItWorksSection`, `ComparisonSection`, `FaqSection`, `ContactSection`, `AboutSection`, `CostEstimatorSection`, `PackageComparisonTable`, `PackageSpecsAccordion`) is called, at every one of its call sites across all standalone pages and the Home one-pager, only with plain `id`/`className`/`showHeading`/`selectedSlug` string/boolean props — grepped across `src/app/(public)` to confirm no other icon- or function-bearing prop crosses a Server→Client boundary anywhere in the app.

## Post-Part-20 fix — RSC serialization bug (real first `npm run dev` run)
- **Bug**: the user's first real `npm run dev` + browser run (after receiving the Part 20 deliverable) hit repeated runtime errors — "Functions cannot be passed directly to Client Components unless you explicitly expose it by marking it with 'use server'..." (once per lucide-react icon in the nav config) and "Only plain objects can be passed to Client Components from Server Components. Classes or other objects with methods are not supported." — on every page under both shells.
- **Root cause**: `src/app/(internal)/admin/layout.tsx` and `src/app/(portal)/dashboard/layout.tsx` are both Server Components (no `"use client"`). Both imported `ADMIN_NAV`/`PORTAL_NAV` (`src/components/shell/nav-config.ts`) and passed them straight through as the `navGroups` prop into `AppShell` — a Client Component. `NavItem.icon` holds a raw lucide-react component (function) reference stored as plain object data, and the React Server Components boundary cannot serialize a function reference (or any object holding one) when it crosses from a Server Component into a Client Component as a prop. This is a **pre-existing latent bug dating back to Part 3** (`AppShell`/`nav-config.ts`'s original design) — Part 20 touched no `src/` files (confirmed via mtime check) and did not introduce it. It was never caught by this project's own static verification (`verify.py`, `verify_imports.py`, `verify_use_client.py`), because none of them run `tsc` or `next dev` — this sandbox has no `node_modules`/network access to install and run either — so this class of runtime-only cross-boundary serialization error was structurally invisible to every check this project could run on its own, and only surfaced once the user started the real dev server.
- **Fix**: `AppShell` (`src/components/shell/app-shell.tsx`, already `"use client"`) no longer takes a `navGroups` prop at all — it now imports `PORTAL_NAV`/`ADMIN_NAV` directly and selects the right one itself from its own existing `variant` prop (`const navGroups = variant === "admin" ? ADMIN_NAV : PORTAL_NAV`). Both `admin/layout.tsx` and `dashboard/layout.tsx` dropped the `navGroups={...}` prop and their now-unused `nav-config` import — the icon-bearing config is now constructed entirely inside the Client Component and never crosses the Server→Client boundary as a prop. Verified: brace-balance check on all 4 touched files, and a full re-check of every other `icon:`-bearing config in the codebase (`MetricCard` usage, `cost-summary.tsx`/`cost-to-complete-summary.tsx`'s `STATUS_STYLE`, `document-category-config.ts`, every public marketing page's local `icon:` arrays) confirmed none of them cross a Server→Client prop boundary the way `nav-config.ts` did — every other instance either lives inside the same Client Component file that consumes it, or is rendered to JSX before it could be passed as a prop.
- **Also fixed in the same pass** (visible in the same terminal output, a warning rather than a hard error): `src/app/layout.tsx` had `themeColor` inside its `metadata` export, which Next.js now warns about ("Unsupported metadata themeColor is configured in metadata export... Please move it to viewport export instead"). Moved to a new, separate `export const viewport: Viewport = { themeColor: "#e31e24" }`, the current Next.js convention.
