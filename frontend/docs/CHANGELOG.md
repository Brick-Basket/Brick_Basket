## Contact section — dropped the forced full-viewport frame that left a dead gap below "Send Message"

The owner reported (with screenshots of `/#contact` scrolled to the bottom) a large, un-eye-catching block of empty beige space below the "Send Message" button, before the closing red bar — and asked for a specific recommendation rather than a single prescribed fix.

- **Root cause**: the section-framing pass immediately above gave `ContactSection` the same `FRAME_GRID` treatment as Hero/About (`min-h-[calc(100vh_-_4rem)] content-center`, so the section always reserves one full screen and vertically centers its content within it). That's the right fix for a section whose *next sibling* is another main-nav anchor that would otherwise peek in early (Home→About, About→Services, etc.). Contact is different: it's the last nav anchor on the page — what follows it is the "We look forward to hearing from you" strip and the closing red CTA band, both intentional page-ending content, not another section that needs to stay hidden. Forcing Contact to fill a full screen just to prevent a "peek" that was never really a problem meant that on any viewport taller than the info-column + form card, `content-center` padded the real content out symmetrically — and since the user was scrolled to the very bottom of the anchor, only the *lower* half of that padding was on-screen, reading as one large orphaned gap under the button.
- **Fix, `src/app/(public)/page.tsx`**: `ContactSection` now gets `className={SCROLL_OFFSET}` (just `scroll-mt-16`, for the anchor-scroll offset under the sticky header) instead of `FRAME_GRID` — no forced minimum height, no `content-center`. The section now sits at its own natural height, so the form card's bottom edge sits directly above the "We look forward..." strip with only its own `py-16 md:py-20` padding, the same as every other in-flow content section. Every other anchored section (Hero, About, Services, Projects, Why Us, FAQ) keeps its full-frame treatment — Contact was the one section where the underlying "prevent next-anchor peek" rationale didn't apply, not a sign the whole approach was wrong.
- **On the owner's own logo suggestion**: recommended against filling the gap with a large logo mark instead of removing the forced height — that would have kept an artificial gap and then decorated it, rather than fixing the layout that created the gap. The site's logo already appears in the header and footer on every page including this one, so a second large placement here would be redundant rather than "eye-catching." If a stronger visual close to the page is wanted later, a better lever is the existing red CTA band immediately below (bigger heading, an image, a background pattern) — happy to build that out on request — but it's a separate, opt-in enhancement, not a fix for this bug.

## Section-framing pass — every one-pager anchor now fills its own screen, no next-section bleed-through

The owner reported (with screenshots of `/#home`, `/#projects`, `/#faq`) that navigating to a nav-bar anchor on the one-pager Home page often showed the next section's heading peeking in at the bottom of the screen — inconsistent from section to section, since a section shorter than the viewport (the hero, a 4-card Projects grid, a short Why Us block) let whatever followed it creep into view the instant you landed, while a taller section didn't. Read as "sections shrinking into the same page" rather than each nav anchor reliably showing one section at a time.

- **`src/app/(public)/page.tsx`**: `SCROLL_OFFSET` (just `scroll-mt-16`) is now joined by two additional constants, `FRAME_GRID` and `FRAME_BLOCK`, both adding `min-h-[calc(100vh_-_4rem)]` (a full viewport minus the sticky header's own `h-16`) so every anchored section reserves at least one full screen — a section whose real content is taller than that (a long FAQ list, e.g.) still scrolls normally past the floor; this only stops a *short* section from coming up short. Two variants because these sections lay out their own top-level element differently: `FRAME_GRID` centers content via CSS Grid's own `align-content` (Hero/About/Contact, whose outer element is itself `grid`); `FRAME_BLOCK` uses `flex flex-col justify-center` (Services/Projects/Why Us/FAQ, whose outer element is a plain block wrapping a heading + inner grid). Applied to all 7 anchored sections (Hero, About, Services, Projects, Why Us, FAQ, Contact).
- **Standalone routes deliberately untouched.** `FRAME_GRID`/`FRAME_BLOCK` are passed only from the one-pager's own `page.tsx` — the standalone `/about`, `/why-us`, `/faq`, `/contact` routes call the exact same shared section components (`AboutSection`, `WhyUsSection`, `FaqSection`, `ContactSection`) with no `className` override at all, so their own shorter, `PageBanner`-topped layout is unaffected. No change to any shared component's own file.
- Caught and fixed before shipping: the first attempt wrote `min-h-[calc(100vh-4rem)]` (no spaces around the minus). Tailwind's arbitrary-value syntax requires escaping spaces as underscores, and CSS `calc()` itself requires whitespace around a `-` operator — `100vh-4rem` isn't valid `calc()` syntax and would have silently failed to apply any minimum height at all. Corrected to `min-h-[calc(100vh_-_4rem)]`.

(once per lucide-react icon in the nav config) and "Only plain objects can be passed to Client Components from Server Components. Classes or other objects with methods are not supported." — on every page under both shells.
- **Root cause**: `src/app/(internal)/admin/layout.tsx` and `src/app/(portal)/dashboard/layout.tsx` are both Server Components (no `"use client"`). Both imported `ADMIN_NAV`/`PORTAL_NAV` (`src/components/shell/nav-config.ts`) and passed them straight through as the `navGroups` prop into `AppShell` — a Client Component. `NavItem.icon` holds a raw lucide-react component (function) reference stored as plain object data, and the React Server Components boundary cannot serialize a function reference (or any object holding one) when it crosses from a Server Component into a Client Component as a prop. This is a **pre-existing latent bug dating back to Part 3** (`AppShell`/`nav-config.ts`'s original design) — Part 20 touched no `src/` files (confirmed via mtime check) and did not introduce it. It was never caught by this project's own static verification (`verify.py`, `verify_imports.py`, `verify_use_client.py`), because none of them run `tsc` or `next dev` — this sandbox has no `node_modules`/network access to install and run either — so this class of runtime-only cross-boundary serialization error was structurally invisible to every check this project could run on its own, and only surfaced once the user started the real dev server.
- **Fix**: `AppShell` (`src/components/shell/app-shell.tsx`, already `"use client"`) no longer takes a `navGroups` prop at all — it now imports `PORTAL_NAV`/`ADMIN_NAV` directly and selects the right one itself from its own existing `variant` prop (`const navGroups = variant === "admin" ? ADMIN_NAV : PORTAL_NAV`). Both `admin/layout.tsx` and `dashboard/layout.tsx` dropped the `navGroups={...}` prop and their now-unused `nav-config` import — the icon-bearing config is now constructed entirely inside the Client Component and never crosses the Server→Client boundary as a prop. Verified: brace-balance check on all 4 touched files, and a full re-check of every other `icon:`-bearing config in the codebase (`MetricCard` usage, `cost-summary.tsx`/`cost-to-complete-summary.tsx`'s `STATUS_STYLE`, `document-category-config.ts`, every public marketing page's local `icon:` arrays) confirmed none of them cross a Server→Client prop boundary the way `nav-config.ts` did — every other instance either lives inside the same Client Component file that consumes it, or is rendered to JSX before it could be passed as a prop.
- **Also fixed in the same pass** (visible in the same terminal output, a warning rather than a hard error): `src/app/layout.tsx` had `themeColor` inside its `metadata` export, which Next.js now warns about ("Unsupported metadata themeColor is configured in metadata export... Please move it to viewport export instead"). Moved to a new, separate `export const viewport: Viewport = { themeColor: "#e31e24" }`, the current Next.js convention.
